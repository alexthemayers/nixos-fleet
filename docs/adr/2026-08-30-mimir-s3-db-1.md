# ADR: Mimir S3 goes to db-1, not the LB

**Status:** superseded (2026-08-30)

Pinning Mimir (and Attic S3) to `proxmox-db-1:3902` hid db-2 404s.
Superseded by
[2026-08-30-garage-s3-lb.md](2026-08-30-garage-s3-lb.md): repair Garage
metadata, keep S3 clients on the LB.

## Context

Mimir compactors and the blocks cleaner talked to Garage through
`proxmox-lb:3902`. Caddy round-robins to `proxmox-db-1` and `proxmox-db-2`.
After Garage restarts, db-2's sqlite merkle tables lagged (`object.MklTodo`
in the tens of thousands). The same key `GET`s as 200 on db-1 and 404 on
db-2. Cleanup treats that 404 as fatal (`read meta file attributes: …/meta.json:
The specified key does not exist`) and never rewrites
`anonymous/bucket-index.json.gz`. Store-gateway then rejects Grafana range
queries with `err-mimir-bucket-index-too-old` (24h `max_stale_period`).

Attic already uses `proxmox-db-1:3902` for the same class of Caddy/S3
failure (truncated NARs on the LB hop).

## Decision

Mimir's S3 endpoint is `proxmox-db-1:3902`. Do not send Mimir through the
LB until db-2's `MklTodo` is 0 and a GET of a known object succeeds on both
nodes.

## Consequences

db-1 is an S3 SPOF for Mimir (already true for Attic). Loki still uses the
LB. `garage repair -a tables` / `blocks` is the way to drain the merkle
backlog; it does not replace this endpoint pin. `restartIfChanged = false`
on Mimir: after switch, restart `mimir.service` on both obs nodes.

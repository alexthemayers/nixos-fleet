# Use Markdown Any Decision Records 3.0

## Context and Problem Statement

This fleet records product and topology freezes as ADRs under `docs/adr/`.
Those files used a short Nygard-style trio (Context, Decision, Consequences)
and a bold **Status** line. How should new and existing decision records be
structured so status, options, and outcome stay explicit?

## Decision Drivers

* Later readers need the question, the options, and why one won.
* Existing relative links use `docs/adr/YYYY-MM-DD-slug.md`.
* Agent rules must point at one template, not a second essay.
* Historical records must not gain invented options.

## Considered Options

* [MADR 3.0.0](https://adr.github.io/madr/) in `docs/adr/`, keep
  `YYYY-MM-DD-slug.md`
* MADR 3.0.0 as upstream does: `docs/decisions/NNNN-title.md`
* Keep Context / Decision / Consequences only
* Formless notes with no template

## Decision Outcome

Chosen option: "MADR 3.0.0 in `docs/adr/`, keep `YYYY-MM-DD-slug.md`",
because MADR makes assumptions explicit and this tree already indexes
date-slug paths. Do not renumber or move files.

New ADRs copy [adr-template.md](adr-template.md). Required sections:
Context and Problem Statement, Considered Options, Decision Outcome,
Consequences. Add Decision Drivers, Validation, Pros and Cons of the
Options, and More Information when they carry information.

Records written before this decision keep their original prose. Headings
and YAML `status` / `date` were mapped onto MADR names; options were not
backfilled.

### Consequences

* Good, because status lives in YAML and the index can list it.
* Good, because a new ADR has a place for rejected options.
* Bad, because older files are thinner than a full MADR and must not be
  "completed" from memory.
* Bad, because this is not upstream's `docs/decisions/` + `NNNN` layout.

## Validation

`.cursor/rules/docs-formatting.mdc` describes the template. A new ADR is
`docs/adr/YYYY-MM-DD-slug.md` with YAML `status` and a row in
[README.md](README.md).
